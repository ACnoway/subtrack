# 订阅与数字资产管理平台开发大纲

**项目暂定名称：SubTrack**

版本：V1.0 开发规划  
项目类型：Go Web 应用 / Docker 自托管（服务端与后台 Worker 使用 Go）
目标用户：拥有多个 VPS、域名及线上订阅服务的个人用户，未来支持多用户

---

## 一、项目概述

### 1.1 项目背景

随着个人购买的 VPS、域名、云计算资源和在线服务数量不断增加，不同服务商的续费周期、收费方式和到期提醒机制存在差异，容易导致：

- 忘记续费造成 VPS 停机、数据丢失
- 域名过期导致网站无法访问，甚至失去域名所有权
- 忘记取消不再需要的自动续费服务
- 无法清楚了解每月、每年的订阅开支
- 服务分散在不同平台，管理成本较高

### 1.2 项目目标

构建一个支持 Docker 部署的轻量化 Web 平台，实现数字资产和订阅服务的集中管理，并通过 Email 和 Telegram 两种渠道发送可靠的续费提醒。

### 1.3 核心设计原则

1. **通知可靠性优先**：提醒任务应支持持久化、失败重试和发送记录。
2. **操作简单**：添加服务尽量只需要名称、类别和到期日期。
3. **独立部署**：无需依赖商业 SaaS 平台。
4. **数据可迁移**：支持导出和备份。
5. **逐步扩展**：初期不依赖服务商 API，后期实现自动同步。
6. **安全性**：不存储服务器 root 密码、域名账户密码等非必要敏感数据。

## 二、功能需求

### 2.1 订阅与资产管理（P0）

支持以下资源类型：

| 资源类型 | 示例 |
|---|---|
| VPS / 独立服务器 | RackNerd、Vultr、Hetzner |
| 域名 | Cloudflare Registrar、Spaceship |
| 云服务 | 对象存储、云数据库 |
| 软件订阅 | IDE、在线办公软件 |
| API 服务 | AI API、第三方付费接口 |
| SSL 证书 | 付费 TLS 证书 |
| 其他 | 任意需要续费的服务 |

每条资产记录支持以下字段：

- 资产名称、类别、描述
- 服务提供商
- 所属账户备注（用于区分不同平台账号）
- 购买日期、到期日期
- 下次扣费日期（可选，允许与到期日期不同）
- 续费周期：月付、季付、半年付、年付、自定义、一次性
- 续费价格、货币单位
- 自动续费状态
- 续费链接
- 优先级、标签、备注
- 生命周期状态：正常、即将到期、已过期、已归档

主要操作：

- 新增、编辑、删除、归档订阅
- 搜索、筛选、排序
- 批量导入与导出
- 手动确认续费
- 保留历史续费记录

### 2.2 到期提醒系统（P0）

系统定时检查数据库中的资产到期时间，生成需要发送的提醒任务。

默认提醒规则：

| 距到期时间 | 普通订阅 | 域名等重要资产 |
|---|---|---|
| 60 天 | 不提醒 | 提醒 |
| 30 天 | 提醒 | 提醒 |
| 14 天 | 提醒 | 提醒 |
| 7 天 | 提醒 | 提醒 |
| 3 天 | 提醒 | 提醒 |
| 1 天 | 提醒 | 提醒 |
| 当天 | 提醒 | 提醒 |
| 已过期 | 持续有限次数提醒 | 高优先级提醒 |

提醒规则可以全局设置，也可以对单个资产进行覆盖。

额外要求：

- 每位用户可以选择通知时区及发送时间。
- 支持同时启用 Email、Telegram。
- 支持单个渠道关闭。
- 支持每日到期摘要和重要资产独立提醒。
- 同一个提醒阶段、同一个渠道在成功发送后不再重复发送。
- 续费日期变更后自动取消旧周期的待发送提醒。
- 对自动续费资产，提醒用户检查扣款和续费是否成功，不默认认定已完成续费。

### 2.3 Email 邮件通知（P0）

使用 SMTP 协议发送邮件。

主要功能：

1. 管理员设置 SMTP Host、Port、用户名、密码及发件人。
2. 用户绑定通知邮箱。
3. 支持发送测试邮件。
4. 使用 HTML 邮件模板。
5. 记录发送时间及发送结果。
6. 发送失败后重试。

邮件内容包括资产名称、服务商、到期日期、剩余天数、续费金额以及续费链接。

### 2.4 Telegram 通知（P0）

使用 Telegram Bot API。

用户绑定流程：

1. 管理员通过 BotFather 创建机器人。
2. 后端配置 Bot Token。
3. 用户在网页设置中点击“绑定 Telegram”。
4. 系统生成带有一次性绑定 Token 的机器人链接。
5. 用户通过 Telegram 打开机器人并发送 `/start`。
6. 后端验证 Token，保存 Chat ID，完成绑定。
7. 发送测试消息。

通知消息支持：

- 资产名称与类型
- 剩余天数和到期时间
- 续费价格
- 续费链接按钮
- 打开管理平台按钮

可扩展的机器人命令：

- `/list`：查看全部资产
- `/upcoming`：查看近期到期项目
- `/summary`：查看订阅概况
- `/help`：查看帮助

后期可以增加 Telegram 消息内直接确认续费或延迟提醒的功能。

### 2.5 续费管理（P0）

用户完成续费后，可以在网页中点击“已续费”。

系统执行：

1. 弹出续费确认窗口。
2. 允许填写新的到期日期和实际支付金额。
3. 对于固定周期订阅，可以自动计算建议的新到期日期。
4. 保存本次续费记录。
5. 根据新日期重新生成提醒计划。
6. 更新资产状态。

注意：自动推算的日期必须允许修改，因为域名、VPS 等服务的实际续费日期可能不完全符合固定周期。

### 2.6 仪表盘（P1）

首页展示：

- 当前订阅总数
- 未来 7 天、30 天到期数量
- 已过期但未确认处理的资产数量
- 每月 / 每年预计订阅支出
- 最近到期的资产列表
- 按类型和服务商统计的费用

支持日历视图、列表视图和图表视图。

不同币种应分别汇总；跨币种合计需要使用可追溯的汇率及换算日期。

### 2.7 通知记录与系统状态（P0）

提供通知历史页面，记录：

- 对应资产
- 提醒阶段
- 通知渠道
- 预定发送时间
- 实际发送时间
- 发送结果
- 重试次数
- 错误信息

管理员可以查看失败任务并手动重新发送。

## 三、技术架构

### 3.1 推荐技术栈

| 模块 | 推荐技术 |
|---|---|
| 主要开发语言 | Go；Web 服务、REST API 和后台 Worker 均使用 Go |
| Web 页面 | Go `html/template` 服务端渲染、HTML、CSS；交互需要时使用少量渐进增强脚本 |
| HTTP 服务 | Go `net/http`，提供网页和 REST API |
| 数据库 | PostgreSQL，通过 Go 数据库驱动访问；使用版本化 SQL 管理结构迁移 |
| 邮件 | Go 邮件发送组件 + SMTP |
| Telegram | Telegram Bot API |
| 定时任务 | 独立 Go Worker，与 Web 服务共享 Go 模块和数据模型 |
| 部署 | Docker Compose |
| 反向代理 | Caddy 或 Nginx |
| 日志 | Go 结构化日志 + 数据库通知记录 |

应用服务端和后台任务以 Go 实现，不依赖 Next.js 或 Node.js 作为运行时。第一版使用一个代码仓库，Web 服务和任务 Worker 可作为独立进程或容器运行。

为了降低个人部署的资源开销，暂时不引入 Redis、Kafka 等额外组件。使用 PostgreSQL 保存任务状态，通过数据库锁或任务认领机制避免并发处理冲突。

### 3.2 系统架构

```text
                  用户浏览器
                      |
                      v
                Go Web 应用
        (html/template 页面 + REST API)
                      |
                      v
                 PostgreSQL
                /           \
               /             \
          资产与用户数据     提醒任务与发送日志
                                |
                                v
                      独立 Go Worker
                                |
                      +---------+---------+
                      |                   |
                      v                   v
                 SMTP 服务          Telegram Bot API
                      |                   |
                      v                   v
                    邮箱              Telegram
```

Go Web 服务、数据库、Go Worker 通过 Docker Compose 统一部署。浏览器界面以服务端渲染为主，减少额外前端构建和运行时依赖。

### 3.3 定时任务设计

建议 Worker 每分钟或每数分钟检查一次到期提醒任务。

任务执行流程：

```text
读取到期任务
    ↓
检查资产状态和最新到期日期
    ↓
原子认领任务
    ↓
检查通知渠道是否启用
    ↓
调用通知发送服务
    ↓
记录成功或失败
    ↓
失败任务进入重试队列
```

关键实现要求：

- 数据库任务持久化，服务重启后仍可继续执行。
- 同一资产、同一续费周期、同一提醒阶段、同一通知渠道建立唯一约束。
- Email 和 Telegram 独立处理，避免其中一个渠道故障影响另一个。
- 支持指数退避重试和最大重试次数。
- 对发送请求已成功但响应丢失的情况，允许极少量重复消息的可能性，不承诺不现实的绝对“仅发送一次”。
- 通过心跳检测监控 Worker 是否持续运行。

第二阶段将通知设置、规则、任务队列和发送历史保存在 PostgreSQL；SMTP 凭据和 Telegram Bot Token 通过环境变量提供。Worker 每 5 秒检查任务并以 Bot API 长轮询接收 `/start` 绑定消息；通知任务提前一年排入队列，单个任务最多自动尝试 5 次。邮件与 Telegram 分别建立任务，因此一个渠道失败不会阻塞另一个渠道。修改规则、到期日、归档状态或关闭渠道时，未发送的过期任务会取消。成功发送的任务不会在后续扫描中重新创建。

交付标准：到期提醒能按配置送达两个渠道，重启应用后未执行任务不会丢失。发送成功但响应丢失时仍可能产生重复消息，符合数据库队列发送模型的 at-least-once 限制。

## 八、未来扩展方向

### 8.1 域名自动检测

通过 RDAP 获取域名注册信息，辅助核对域名到期日期。

需要区分注册商到期日期和注册局到期日期，以用户注册商后台显示的续费截止日期为重要依据。

当自动检测结果与数据库记录不一致时，先提示用户确认，不直接覆盖。

### 8.2 服务商 API 集成

设计统一适配器接口：

```go
type ProviderAdapter interface {
    ValidateCredentials(ctx context.Context) error
    ListResources(ctx context.Context) ([]Resource, error)
    GetResourceDetails(ctx context.Context, id string) (Resource, error)
}
```

在此基础上接入具体服务商的 API，实现资源发现、到期日期同步和价格同步。

### 8.3 账单导入

支持 CSV 或其他结构化账单文件导入，逐步实现支付记录与现有资产的关联。

### 8.4 移动端优化

初期采用响应式 Web 设计；后期可考虑 PWA，实现手机桌面快捷访问。

## 九、安全性与运维

1. **认证与授权**：首版采用单管理员账户，预留用户归属字段。
2. **HTTPS**：对公网提供服务必须启用 HTTPS。
3. **敏感信息保护**：SMTP 密码、Bot Token 等通过环境变量或受保护的密钥配置管理。
4. **备份**：PostgreSQL 定期备份，支持异机存储与恢复测试。
5. **健康检查**：检测 Web 服务、数据库、通知 Worker 状态。
6. **故障隔离**：建议不要仅把管理系统部署在唯一需要监控续费的 VPS 上，或配置独立的外部心跳告警。
7. **安全日志**：不在应用日志中输出密钥、SMTP 密码或绑定 Token。
