# 版本管理与 Docker 镜像发布

## 版本规则

正式版本以 Git tag 为唯一版本来源，格式为 `vMAJOR.MINOR.PATCH`，例如 `v0.1.0`、`v1.2.3`。数字不得有前导零，不使用额外的版本文件。

- `MAJOR`：不兼容变更，例如部署配置或接口发生破坏性变化。
- `MINOR`：向后兼容的新功能。
- `PATCH`：向后兼容的问题修复。
- `0.x.y` 表示尚未稳定的开发阶段；不兼容调整提升次版本，兼容修复提升修订版本。
- `v1.0.0-rc.1`、`v1.0.0-beta.1` 等预发布版本、带 `+` 的构建元数据 tag 不发布镜像。

发布者应从已合并并验证的 `main` 提交创建 tag，按版本号递增、一次发布一个版本，并等待上一次发布成功后再推送下一个 tag。工作流只检查 tag 格式，不强制检查分支归属或版本递增。正式 tag 一经发布，不得删除、移动或复用；修复已发布版本需要创建新的 PATCH 版本。

## 一次性配置

1. 项目使用 Docker Hub 镜像仓库 `acnofun/subtrack`。需要公开拉取时将仓库设为 Public。
2. 创建具有该仓库写入权限的 Docker Hub Access Token。
3. 在 GitHub 仓库的 **Settings → Secrets and variables → Actions** 中配置：

| 类型 | 名称 | 示例或用途 |
|---|---|---|
| Variable | `DOCKERHUB_USERNAME` | Docker Hub 登录用户名 |
| Variable | `DOCKERHUB_IMAGE` | 完整镜像名 `acnofun/subtrack`，必须小写，不带 tag 或 `https://` |
| Secret | `DOCKERHUB_TOKEN` | 具有目标仓库写入权限的访问令牌 |

组织镜像可将 `DOCKERHUB_IMAGE` 设置为 `organization/subtrack`，登录账号须有该仓库的写权限。不要把令牌写进 Git 或 `.env.example`。确保仓库已启用 GitHub Actions，且允许工作流使用所列的官方 actions。

## 触发与镜像标签

工作流位于 [docker-publish.yml](../.github/workflows/docker-publish.yml)，自动发布只监听正式版本 tag 的 push。普通分支 push、PR、预发布 tag 和单独编辑 GitHub Release 不触发自动构建。必须先将工作流提交到默认分支，再推送该提交的 tag。

工作流也提供 `workflow_dispatch` 手动入口，可在 Actions 页面选择已存在的正式版本 tag，按需补发或恢复发布；手动入口仍会校验 tag 格式，并从该 tag 对应的源码构建。它不改变自动发布仍由版本 tag 触发的规则。

触发器使用 GitHub 的 glob 模式匹配数字版本，工作流还会严格校验版本格式。像 `v01.2.3` 这样的非法 tag 可能启动工作流，但会在构建和登录前失败，不发布镜像。

推送 `v1.2.3` 后，流程依次执行 Go 测试与 vet、构建 `linux/amd64` 和 `linux/arm64` 镜像、推送 Docker Hub。Dockerfile 使用 Go 交叉编译，无需 QEMU。构建缓存保存在 GitHub Actions 中。

| Docker 镜像标签 | 含义 |
|---|---|
| `acnofun/subtrack:1.2.3` | 对应 Git tag `v1.2.3` 的固定版本，部署推荐使用 |
| `acnofun/subtrack:latest` | 最近一次成功发布的正式版本 |

不生成 `1` 或 `1.2` 等滚动标签。`latest` 跟随最后成功的发布任务，不比较版本大小，因此不要重跑旧版本或并发推送多个版本；旧版本重跑可能使 `latest` 回退。正式版本标签按项目规则保持不变，工作流本身不会阻止 Docker Hub 上的覆盖。生产环境需要不可变引用时可固定镜像 digest。

## 发布步骤

先完成代码检查、文档更新，涉及数据库变更时说明迁移和回滚限制。以下以首次发布 `v0.1.0` 为例：

```sh
git switch main
git pull --ff-only origin main
go test ./...
go vet ./...
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin v0.1.0
```

每次只推送一个明确的 tag，不使用 `git push --tags`。到 GitHub Actions 查看 **Publish Docker image** 的结果；成功后在 Docker Hub 检查版本标签和两个平台。可选地创建同名 GitHub Release 编写更新说明，该操作不会重复触发工作流。

```sh
docker buildx imagetools inspect acnofun/subtrack:0.1.0
```

若仅因网络或凭据问题失败，可修复配置后在 Actions 中重跑原任务；前提是没有更新版本已发布，且 tag 对应的源码没有变化。若需要修改源码或工作流，应提交修复并使用新的版本 tag。

## 使用已发布镜像部署

`compose.release.yaml` 包含 Web、通知 Worker 和 PostgreSQL，可单独用于部署，无需与开发 Compose 文件合并。Web 和 Worker 使用同一个应用镜像，Worker 通过 `command: ["worker"]` 启动。默认镜像为 `acnofun/subtrack:latest`。如需固定到某个版本，同时修改 `app.image` 和 `worker.image`：

```yaml
image: acnofun/subtrack:0.2.0
```

在项目目录运行：

```sh
docker compose -f compose.release.yaml up -d
docker compose -f compose.release.yaml ps
docker compose -f compose.release.yaml logs -f app
docker compose -f compose.release.yaml logs -f worker
```

Release 文件会按各服务 `image` 中的引用从 Docker Hub 拉取镜像，并始终检查远程镜像。PostgreSQL、运行环境变量和数据卷都在该文件中定义。SMTP 与 Telegram Bot 凭据、通知邮箱、时区、提醒规则及发送时间均在网页的“提醒设置”中管理；SMTP 密码和 Bot Token 加密保存在 PostgreSQL。旧版 `.env` 中的通知变量会在升级后首次启动时导入一次，确认配置已出现在网页后即可从 `.env` 删除。保留 `SESSION_SECRET` 原值并与数据库备份一同保管，否则无法解密已保存的通知凭据。更新时先备份数据库，再修改 Web 与 Worker 的镜像 tag 并重新执行启动命令。私有镜像需要先执行 `docker login`。

回滚时将 Web 与 Worker 的 `image` 改为同一已发布的旧版本并重新启动；应用启动时会自动迁移数据库，退回镜像不会撤销迁移。`v0.2.0` 新增通知设置、提醒任务和发送历史迁移；`v0.3.0` 新增自定义续费周期天数及 `renewal_records` 续费历史表；`v0.3.1` 新增 `integration_settings` 通知渠道配置表，旧版应用不会读取或修改该表。回滚到 `v0.3.0` 后，旧版仍会从环境变量读取 SMTP 和 Telegram 凭据；如要使用旧版通知功能，需暂时恢复旧 `.env` 配置。数据库迁移不会撤销或删除通知配置。若要回滚数据库，请先备份并评估迁移后的数据兼容性后恢复备份。
